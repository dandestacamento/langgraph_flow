## Per-question detail

### 1. "What is a Python decorator?" — Level 1 (simple topic routing)
**Routing chain**: `complexity_router` (simple) → `topic_router` (python,
confidence 1.0) → `subtopic_router` (fundamentals) → `chapter_selector`
(chapter_02_decorators) → `rag_retriever` → `tool_router` (no tool
needed) → `python_agent` → `synthesis_agent` (free pass-through, 1
topic).
**Answer**: Correctly explains decorators, `functools.wraps`, and the
mutable-default-argument pitfall — all three retrieved chapters'
content, cited accurately.
**Comment**: The baseline case — every router was fully confident (topic
1.0), no tool, no retry. This is what ~90% of real traffic in this
project's own experiment looked like.

### 2. "What's the difference between a VNet and a subnet in Azure?" — Level 2 (subtopic routing)
**Routing chain**: same shape as #1, landing on `azure_cloud` /
`networking` / `chapter_01_vnet`.
**Answer**: Correctly distinguishes VNet (isolated network boundary) from
subnet (a CIDR-scoped subdivision of it) — this specific fact spans two
chapters (`chapter_01_vnet`, `chapter_02_subnets`), both of which were
retrieved and cited even though `chapter_selector` only picked one as
"the" chapter — a good demonstration of why retrieval stays scoped to
subtopic rather than the single chapter guess (see `app/rag/retrieval.py`'s
docstring).

### 3. "What does `spark.sql.shuffle.partitions` default to?" — Level 3 (chapter routing)
**Routing chain**: `data_engineering` / `spark` / `chapter_02_partitions` —
all three selections correct.
**Answer**: "...defaults to 200." — correct, exact figure from the
source chapter.
**Comment**: Only 1,280 cached input tokens here vs. ~3,072 for most
others — a partial cache miss (this exact question+context combination
hadn't been asked in quite this form before), still cheap either way.

### 4. "What is the maximum amperage draw of the RF-900 refrigerator's compressor?" — Level 4 (RAG + insufficient-info)
**Routing chain**: `appliances` / `refrigerators` / `chapter_01_overview`
→ **`tool_router` decided a tool WAS needed** (`sql_query`, query
`SELECT compressor_amperage FROM specifications WHERE model = 'RF-900'`)
→ that query genuinely fails (no such column, no such model) →
**recovery was attempted** (`reason: tool_error`) → still correctly
failed → final answer: *"Insufficient information..."*
**Comment**: This is the same natural tool-error-recovery finding
documented in the Level 10 README section, reproduced live here — the
Tool Router hallucinates a plausible column name for a fact that was
never in the knowledge base, the SQL genuinely errors, the one bounded
recovery retry correctly also fails, and the system still doesn't
fabricate an answer. This is correct behavior, not a bug: there is no
RF-900 model in the knowledge base at all.

### 5. "Is it covered?" — Level 5 (ambiguous question / clarification)
**Routing chain**: `complexity_router` → `topic_router` (flagged
`is_ambiguous: true`) → **routes straight to `clarification_agent`**,
skipping subtopic/chapter/retrieval entirely (`selected_subtopics` and
`selected_chapters` are correctly empty — no guess was ever made).
**Answer**: *"What specific item or service are you inquiring about
regarding coverage?"*
**Comment**: Textbook correct Level 5 behavior — no product/order/fault
code is named, "it" has no identifiable referent, so the system asks
rather than guesses. Cheapest run of the 10 (only 2 LLM calls) since it
short-circuits before any retrieval happens.

### 6. "What does E21 mean on the WM-500, and what is its standard warranty term?" — Level 6 (multi-chapter evidence)
**Routing chain**: single topic (`appliances`/`washing_machines`), but
retrieval surfaced **three different chapters**
(`chapter_03_faults` ×2, `chapter_01_types`, `chapter_02_operation`) for
one compound question.
**Answer**: "E21: Drainage problem... The WM-500 has a 2-year standard
warranty." — both facts present and correctly sourced from two separate
chapters, not just the single `chapter_selector` guess
(`chapter_03_faults`).
**Comment**: Demonstrates exactly why Level 6 exists — a single-chapter
answer would have missed the warranty-term half of the question.

### 7. "My WM-500 is showing error E21 - is that covered under warranty, and what's SmartHome's standard refund policy?" — Level 7 (multi-topic)
**Routing chain**: **two topics selected** (`appliances`,
`customer_support`) → `subtopic_router`/`chapter_selector`/`rag_retriever`/
`tool_router` each ran **twice** (once per topic, in parallel via
LangGraph's `Send` fan-out) → both topic agents answered independently →
`synthesis_agent` made a real extra LLM call to merge them (unlike
questions 1-6, where synthesis was a free pass-through).
**Answer**: Correctly covers both halves — the E21/warranty explanation
*and* the 30-day refund window/15% restocking fee nuance — with sources
cited from both topics, merged into one coherent response.
**Comment**: The most expensive question in this set by a wide margin
(14 execution-log entries, $0.00148) — exactly the kind of question
where this project's own architecture-comparison experiment showed the
simpler architectures (A/B) completely fail (36% accuracy) since they
can only ever answer one topic. This one succeeded fully.

### 8. "What's the price of the WM-900 washing machine?" — Level 8 (tool selection)
**Routing chain**: `tool_router` correctly recognized price isn't in any
chapter's prose and selected `sql_query` with
`SELECT price_aud FROM specifications WHERE model = 'WM-900'` — this
query succeeds (valid model, valid column).
**Answer**: "$1499 AUD", cited as `tool:sql_query` alongside the chapter
citations.
**Comment**: Clean contrast with question 4 — same tool, same kind of
query shape, but this time the model and column both genuinely exist, so
it succeeds on the first attempt with no recovery needed.

### 9. "Which washing machine model has the largest capacity, and what's its price?" — Level 9 (multi-hop reasoning)
**Routing chain**: `multihop_router` correctly flagged this as genuine
multi-hop (hop 2's subject — "its price" — isn't nameable until hop 1
resolves) → `multihop_agent` took over, recursively running the **entire
pipeline twice**: hop 1 (`hop1:...` prefixed nodes) resolved "largest
capacity" → **WM-900**, then hop 2 (`hop2:...` prefixed nodes) looked up
WM-900's price via `sql_query` → $1499 → a final synthesis LLM call
combined both hops.
**Answer**: "...the WM-900, which has a capacity of 11 kg. The price of
the WM-900 is $1499 AUD." — both the identification and the dependent
lookup are correct.
**Comment**: The most complex question in this set — 21 execution-log
entries (two full sub-pipelines plus bookkeeping), the highest token
count (12,103) and cost ($0.0019) of the 10, exactly as expected for the
most capable mechanism in the whole project.

### 10. "Does SmartHome offer same-day delivery?" — Level 10 (error recovery)
**Routing chain**: `customer_support`/`delivery`/`chapter_01_shipping_methods`
→ first attempt declines (same-day isn't mentioned) → **recovery
attempted** (`reason: insufficient_info`, retrieval broadened to the
whole `delivery` subtopic, dropping the chapter-level narrowing) → still
correctly declines.
**Answer**: *"Insufficient information in the knowledge base to answer
this question."*
**Comment**: Correct — only Standard/Express/White Glove shipping exist
in the knowledge base. The recovery mechanism did its job (broadened the
search before giving up, rather than giving up on the first narrow
attempt), and still reported honestly rather than inventing a same-day
option.

## A bug found and fixed while building this report

Question 9 (the multi-hop one) initially **crashed** both my test script
and would have crashed the Streamlit dashboard's "Ask a question" tab
too: `multihop_agent`'s result never set `selected_topics` at the top
level (it bypasses `topic_router` entirely, see `app/graph.py`), but the
dashboard unconditionally reads `result["selected_topics"]`. Fixed in
`app/agents/multihop_agent.py` by surfacing the union of both hops' own
topic selections — Level 9's test suite (30 tests) still passes, and the
dashboard will no longer crash on a genuine multi-hop question.
