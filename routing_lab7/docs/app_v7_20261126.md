# Routing Lab 7: accuracy and production/enterprise readiness plan

Status: **proposed plan, not implemented.** Baseline: the feature inventory in
[app_v6_20261125.md](./app_v6_20261125.md). Infrastructure background:
[routing-lab-prod-plan.md](../../instructions/learnings/routing-lab-prod-plan.md)
(Keycloak, PostgreSQL, LiteLLM, observability, Azure mapping). This plan does
not repeat that document; it identifies what is still missing in `routing_lab7`
and orders the work.

## 1. Goal and how "accurate" will be defined

Goal: users get answers that are correct, supported by the knowledge base, and
honest about uncertainty, from a service an enterprise can operate, secure and
audit.

No LLM application can be guaranteed 100% accurate, so "accurate" is defined by
measurable targets that gate every release (Section 7):

| Metric | Definition | Proposed release target |
| --- | --- | --- |
| Faithfulness | Share of answer claims supported by the cited passages | >= 98% |
| Answer correctness | Expected facts present, on a held-out golden set | >= 95% |
| Citation validity | Cited passage actually supports the claim it is attached to | >= 95% |
| Correct abstention | Out-of-scope or unanswerable questions get a decline/clarification | >= 95% |
| False abstention | Answerable questions that are wrongly declined | <= 5% |
| Routing accuracy | Topic/subtopic/chapter on the golden set | >= 97% |
| Prompt-injection and leakage | Red-team suite blocked | 100% of known cases |

Targets are starting proposals to confirm with stakeholders (Section 9), and
should be re-based once the larger golden set in Phase 1 gives real numbers.

## 2. Where the app stands today (from code, not assumptions)

Strengths already in place: LangGraph routing with ambiguity detection and
multi-hop decomposition; hybrid retrieval and reranking (optional); one bounded
recovery retry; Keycloak token verification with thread ownership; PostgreSQL
persistence; LiteLLM per-user budgets; guardrail module; MLflow tracing;
batch/NIST/dishwasher regression runners (latest recorded runs 15/15, 12/12,
20/20); a React UI with retrieved-passage previews.

Gaps that matter for accuracy:

1. **Answer verification is conditional.** In
   [_shared.py](../app/agents/_shared.py), `_answer_is_supported` runs only when
   a retrieved passage is an uploaded document (`needs_verification`). Answers
   from the curated knowledge base, and from tool results alone, are never
   checked.
2. **Sources are retrieval references, not citations.** `_source_labels` lists
   everything retrieved, marked "retrieved, not verified". Claims are not
   linked to passages.
3. **Weak automated scoring.** [answer_metrics.py](../app/evaluation/answer_metrics.py)
   uses substring matching and lexical-overlap groundedness; the LLM judge is
   optional and advisory. A pass is not evidence of correctness.
4. **Small, partly overfit test sets.** Golden data is ~228 routing questions
   plus 15 NIST and 12 dishwasher questions; the knowledge base chapters are
   short, synthetic text. The `nist_regression_v4` run (13/15) versus later
   15/15 runs suggests prompts were tuned against the same questions, so those
   scores likely overstate accuracy on unseen questions.
5. **Retrieval defaults are unproven.** Default is plain similarity, top 5,
   no reranking; hybrid/rerank are off "without benchmarked evidence". Retrieval
   has no relevance threshold, so weak evidence still reaches the generator.
6. **Single model, single pass.** Routers and agents share `gpt-4o-mini` at
   temperature 0, with no model-version pinning or regression gate on model
   changes.
7. **Cache can mask regressions.** The persistent LLM/embedding cache is on by
   default; evaluations can pass on cached answers.

Gaps that matter for production/enterprise:

1. Guardrails are **off by default**, input-only injection scanning plus a
   narrow regex secret scanner; no PII handling.
2. Keycloak runs `start-dev` (in-memory H2, no HTTPS); LiteLLM uses dev
   master/salt keys; Compose has plaintext dev passwords.
3. **No authorization model beyond "authenticated".** Knowledge documents are
   shared by all signed-in users; there are no roles or per-document access.
4. **Single-process constraint**: replacement publication is coordinated in one
   backend process; Chroma is a local directory. This blocks horizontal scaling
   and HA.
5. Document registry is in memory without `CHAT_DB_URL`; fall-back modes
   (InMemorySaver, no budgets, taxonomy in SQLite) silently weaken production
   behavior instead of failing at startup.
6. No explicit LLM timeout/retry/circuit-breaker policy in `app/`; no
   structured logging, request IDs, metrics, or alerting (MLflow is a dev
   tool run on demand).
7. CI: [azure-pipelines.yml](../../azure-pipelines.yml) still targets
   `routing_lab3` paths and a self-hosted agent; nothing runs lab 7. No
   Dockerfile for the backend (only the frontend has one), no IaC, no
   documented backup/restore, retention or audit trail.
8. CORS allows `allow_headers=["*"]`; no rate limiting at the API edge, request
   size limits review, or upload malware scanning.

## 3. Workstream A: answer accuracy

### A1. Verify every answer, not only uploaded-document answers
- Run the support check for all answers (curated, upload, tool-only), with the
  setting configurable to a cheaper sampled mode if cost/latency is an issue.
- Replace the single boolean verdict with claim-level checking: split the
  answer into atomic claims, label each `supported / unsupported / contradicted`
  against specific passages (structured output, schema extends `_AnswerCheck`).
- Policy on failure: one regeneration constrained to supported claims; if still
  failing, return the supported part with an explicit "could not verify X"
  note, or decline. Never silently ship an unsupported claim.
- Keep the check on a different model than the generator where possible, to
  reduce correlated errors.

### A2. Real citations
- Number passages in the prompt and require inline markers (e.g. `[2]`) per
  claim; validate that every marker exists and that the A1 check supports that
  claim from that passage.
- Show only passages actually cited, with the others available under
  "also retrieved". Update the UI source list and
  [RoutingDetails](../frontend/src/components/RoutingDetails.tsx) accordingly;
  remove the "retrieved, not verified" label only for claim-verified sources.
- Preserve existing page/version/document metadata.

### A3. Retrieval quality
- Run the existing comparison script
  ([compare_retrieval_modes.py](../scripts/compare_retrieval_modes.py)) on the
  expanded golden set (A5) and choose defaults by evidence: similarity vs
  hybrid vs hybrid + rerank, top-k, candidate pool, chunk size/overlap.
- Add a minimum-relevance gate: when the best score is below a calibrated
  threshold, skip generation and abstain or ask for clarification. Calibrate
  per retrieval mode, since scores are not comparable (per v6 doc).
- Add query rewriting/expansion only if the benchmark shows recall gains.
- Metadata filters (document, version, date) as a first-class retrieval input
  and "answer is stale" handling for superseded versions.

### A4. Abstention and ambiguity
- Add an explicit out-of-scope class to the routing golden set and gate on it;
  today the tests mostly measure routing among in-scope topics.
- Calibrate the `is_ambiguous` flag with a labeled set (false clarification
  rate is a user-experience cost, missed ambiguity an accuracy cost).
- Add fixed, reviewed wording for decline/clarify/unverified states so they are
  consistent and testable.

### A5. Evaluation program (the foundation for everything else)
- Build a **golden set of 300-500 questions**, written/reviewed by subject
  matter owners against real source documents (not the synthetic chapters
  only): factual, multi-chapter, multi-hop, numeric/tool, ambiguous,
  out-of-scope, adversarial, and multi-turn follow-ups. Each with expected
  facts, expected source passages, and expected behavior.
- Split into **tuning** and **held-out** sets; prompts and thresholds are tuned
  on the first only, release gating uses the second. Rotate the held-out set
  periodically to limit overfitting.
- Scoring: keep deterministic checks, add an LLM-judge (different model,
  rubric-based) for faithfulness/correctness, calibrate it against a human-
  labeled sample (report agreement), and keep human review for failures.
- Run with `ROUTING_LAB_CACHE_ENABLED=0` for release gates; cached runs are
  only for fast developer loops.
- Report per-slice results (topic, question type, source type) with confidence
  intervals; a small suite hides regressions.

### A6. Model and prompt management
- Pin model versions (or gateway aliases) in configuration; add a
  model-change procedure: run the full gate before switching.
- Version prompts alongside code with changelog; record prompt/model/index
  versions in every trace and stored answer for reproducibility.
- Evaluate a stronger model for generation/verification only (routers can stay
  cheap) and record the cost/accuracy trade-off.

### A7. Feedback loop
- Thumbs up/down plus reason on each answer, stored with the trace ID;
  triage queue; confirmed failures become golden-set cases.
- Review sample of production answers (e.g. low-confidence, declined,
  unverified) weekly.

## 4. Workstream B: production readiness

### B1. Reliability
- Explicit timeouts, bounded retries with jitter, and circuit breaking for LLM,
  embedding, and gateway calls; define degraded behavior (clear user message,
  no partial unverified answer).
- Fail fast at startup in production mode when required services/settings are
  missing (PostgreSQL, Keycloak issuer, LiteLLM, guardrails) instead of silently
  using the in-memory fallbacks. Keep fallbacks for explicit development mode.
- Graceful shutdown, readiness vs liveness endpoints (`/health` should check
  dependencies; add `/ready`).
- Idempotent ingestion and recovery of interrupted jobs; durable queue for
  indexing instead of an in-process task.

### B2. Scalability
- Move the vector index from local Chroma to a networked store (e.g. pgvector
  in the existing PostgreSQL, or a managed search service) so multiple stateless
  API replicas can run; replace in-process replacement coordination with
  database transactions/locks.
- Containerize the backend (Dockerfile, non-root, pinned dependencies,
  lockfile); externalize local-disk uploads to object storage.
- Load test (Locust, per the prod plan) with target latency/error budgets, e.g.
  p95 end-to-end, concurrent users, and cost per answer; use results to size
  replicas and set rate limits.

### B3. Observability and operations
- Structured JSON logs with request/trace IDs, user pseudonym, model, tokens,
  cost, latency, verification verdict; no raw secrets or full documents.
- Metrics and alerts (OpenTelemetry/Prometheus-compatible): error rate,
  latency, abstention rate, unverified-answer rate, guardrail blocks, budget
  exhaustion, queue depth. Online accuracy proxies matter more than uptime
  alone: alert on a rising unverified/abstain rate or retrieval-score drift.
- Run MLflow (or an OTel backend) as a managed, always-on service in
  deployed environments only. For local development keep the existing
  on-demand-only behavior.
- Runbooks, SLOs, on-call ownership, incident template.

### B4. Delivery pipeline
- Update CI to lab 7 (paths, name, Dockerfile build, dependency audit,
  lint/type-check, unit tests without LLM calls via fakes, frontend tests and
  Playwright).
- Two-tier evaluation: fast PR smoke set (cached or small), and a full
  uncached golden-set gate on release candidates and on any change to prompts,
  models, chunking, embeddings, or knowledge base content. Fail the build on
  threshold regressions from Section 1.
- Environments (dev/staging/prod), IaC (e.g. Bicep/Terraform per the Azure
  mapping in the prod plan), migrations, versioned releases, rollback.
- Knowledge-base changes get the same gate: re-index in staging, run
  evaluation, then promote the index (blue/green index alias).

## 5. Workstream C: security, privacy and enterprise controls

- **Identity**: production Keycloak (or the customer IdP) with persistent
  database, HTTPS, hardened realm, MFA/SSO; remove demo users and dev secrets
  from the shipped config; secrets in Key Vault or equivalent.
- **Authorization**: roles (user, KB editor, admin); restrict knowledge
  upload/reclassify/delete; optional per-document/group access with retrieval
  filtering enforced server-side so users never retrieve content they cannot
  open. Audit-log every knowledge and admin action (who, what, when, version).
- **Guardrails**: enable by default in production; add output-side checks for
  PII, policy violations and indirect prompt injection from uploaded documents
  (treat retrieved text as untrusted; already done in the support check, extend
  to generation); expand the secret scanner; red-team suite in CI.
- **Upload safety**: size/type limits, malware scanning, content-type
  validation, and per-user quotas; sandboxed extraction.
- **API hardening**: edge rate limiting, tighter CORS (explicit headers),
  security headers, request size limits, dependency/vulnerability scanning,
  SBOM, TLS everywhere.
- **Data governance**: retention and deletion policy (conversations,
  attachments, traces), encryption at rest, backup/restore with tested
  recovery, data-residency decision, PII redaction in logs/traces, DPA with
  the model provider (no training on customer data), subject-access/delete
  procedure.
- **Compliance posture**: map controls to the target framework (SOC 2/ISO
  27001/NIST AI RMF, the latter already in the sample knowledge). Document
  model cards, intended use, known limitations.
- **User-facing honesty**: UI states that answers come from the knowledge base,
  shows verified citations, surfaces "unverified/declined" clearly, and offers
  report-a-problem.

## 6. Phased delivery

| Phase | Scope | Exit criteria |
| --- | --- | --- |
| 0. Baseline (1 week) | Freeze current behavior; run all datasets uncached; record metrics, latency and cost; define Section 1 targets with owners | Baseline report committed; targets signed off |
| 1. Evaluation foundation (2-3 weeks) | A5 golden/held-out sets, calibrated judge, uncached gating script, per-slice reports, CI smoke | Golden set reviewed; one command produces the full scorecard |
| 2. Accuracy core (3-4 weeks) | A1 universal claim-level verification, A2 citations, A3 benchmark-driven retrieval defaults and relevance gate, A4 abstention set | Faithfulness, citation, abstention targets met on held-out set |
| 3. Reliability and security baseline (3-4 weeks, parallel with 2) | B1, B4 pipeline for lab 7, Dockerfile, production-mode startup checks, guardrails default-on, C auth hardening and RBAC | Staging deploys from CI; fail-fast verified; red-team suite passes |
| 4. Scale and operations (3-4 weeks) | B2 shared vector store and object storage, multi-replica; B3 metrics/alerts/runbooks; load tests | Load test meets SLOs on >=2 replicas; alert drills done |
| 5. Governance and launch (2-3 weeks) | C data retention, audit logs, compliance mapping, backup/restore drill, A6/A7 feedback loop, pilot with real users | Security review closed; restore tested; pilot accuracy matches golden-set results |

Order of value: Phase 1 first (nothing else can be shown to improve accuracy
without it), then 2 and 3 in parallel.

## 7. Release gate (every release candidate)

1. Uncached golden held-out run meets all Section 1 targets, with no slice
   regressing beyond an agreed margin versus the previous release.
2. Unit, API, frontend and e2e suites pass; no new high/critical dependency
   vulnerabilities.
3. Red-team/guardrail suite passes.
4. Load test within SLOs for changes touching the request path.
5. Prompt, model, embedding and index versions recorded; rollback path tested.

## 8. Risks and trade-offs

- **Latency and cost**: universal claim-level verification adds model calls.
  Mitigate with a small verifier model, parallel claim checks, and measured
  trade-offs; track cost per answer in the scorecard.
- **Over-abstention**: stricter verification and thresholds raise false
  declines. Both false-abstention and unsupported-answer rates are gated.
- **Judge unreliability**: LLM judges are themselves approximate; calibrate
  against human labels and keep humans for borderline and failing cases.
- **Knowledge quality limits accuracy**: a correct answer depends on correct,
  current source documents. Assign content owners and a review cadence.
- **Migration risk** from local Chroma/in-process coordination to shared
  storage; run both in parallel and compare retrieval results before cutover.
- **Eval overfitting**: held-out rotation and fresh production-derived cases.

## 9. Decisions needed before Phase 1

1. Target users, document types and data sensitivity (drives C).
2. Cloud and identity provider (Azure per the prod plan? customer IdP?).
3. Accuracy targets and acceptable latency/cost per answer.
4. Who owns the golden set and knowledge content, and their review capacity.
5. Is a hosted model provider acceptable for the data, or is a private
   deployment required?
6. Compliance frameworks that must be demonstrated at launch.
7. Expected concurrency and availability SLO.

## 10. Out of scope for this plan

Replacing the routing architecture, adopting a paid LangGraph server (see the
licensing finding in the prod plan), or changing the user-facing product
scope. Those can be revisited if the Phase 0 baseline shows routing is a main
source of errors.
