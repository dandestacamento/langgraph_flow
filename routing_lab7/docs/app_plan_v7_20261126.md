# Routing Lab 7: implementation plan

Status: **started; most work remains proposed**.
This is the delivery plan for [app_v7_20261126.md](./app_v7_20261126.md),
not a claim of production readiness or guaranteed accuracy. Preserve the
current routing architecture and development workflow unless a phase
explicitly changes them. The estimates below are planning ranges, not
commitments.

## 1. Review of the proposal

The proposal has the right priorities: establish an independent accuracy
baseline, improve grounding and citations, then demonstrate production
controls and operations. Before implementation, account for these details:

- The listed 15/15, 12/12 and 20/20 are historical **batch report** results,
  not independently verified answer accuracy. The general report lists
  19/19 scored answers and 20/20 overall; the existing
  [answer metrics](../app/evaluation/answer_metrics.py) use fact substrings
  and lexical overlap, and an empty expected-facts list scores as 1. Do not
  treat these results as release evidence.
- The final answer can change after a topic answer is checked: multi-topic
  [synthesis](../app/agents/synthesis_agent.py) and
  [multi-hop synthesis](../app/agents/multihop_agent.py) make additional model
  calls. The [chat graph](../app/chat/graph.py) also answers attachment and
  conversation-history questions outside the knowledge routing graph. A
  universal policy must cover these paths and the final delivered answer,
  not just the specialist agent.
- Existing source labels describe retrieved material, not proof of support.
  An automated claim verifier is also fallible: even if it approves a source,
  label it as **automatically checked**, not guaranteed correct or
  human-verified.
- Do not use the hybrid retrieval display score as a relevance threshold:
  [retrieval.py](../app/rag/retrieval.py) assigns it by rank, not relevance.
  Calibrate a meaningful signal separately for each configuration; if none
  discriminates reliably, use evidence assessment and abstention rather than
  inventing a cutoff.
- The proposal mentions sampled verification for cost and universal
  verification for safety. **Production must verify every applicable answer**;
  sampling may be used for offline monitoring, not to bypass the release
  policy. A verifier error, malformed result or timeout is not a pass.
- The proposal suggests `/health` dependency checks and `/ready`. Keep
  liveness independent of downstream outages and use readiness for required
  dependencies, subject to the deployment platform's probe contract.
- Existing local credentials and Compose settings are explicitly for
  development. Never deploy them to production; removing or changing local
  development credentials is a separate compatibility decision.

### Applying the corrected curated sources

The shared index was not rebuilt for these changes and can still serve the old
wording. Before updating it, stop concurrent writers and back up the index,
manifest, document registry and uploaded originals. An ordinary
`scripts/build_index.py` run can fall back to a full rebuild and delete
uploaded chunks: an operator must first verify that the existing manifest is
present, nonempty, and has the current ingestion signature, and review its
changed and deleted chapter entries. Do not use `--rebuild` on an index
containing uploads. After an approved incremental update, restart the backend
and run uncached regressions; restore from backup if verification fails.

## 2. Decisions and prerequisites

The product owner, security owner, operations owner and domain experts must
agree on the following before committing to a production design or release:

1. Intended users, allowed use cases, data sensitivity, document ownership,
   source freshness, and whether regulated or consequential decisions are in
   scope. Identify cases requiring human escalation.
2. Azure or another environment, identity provider, model/data-processing
   requirements, residency, contractual restrictions, and compliance framework.
3. Whether a shared knowledge base is acceptable or tenant/group/document
   isolation is required. Until approved, shared KB access is **not** suitable
   for sensitive enterprise data. Choose roles and admin workflows.
4. Approve accuracy targets, required slice coverage, availability, recovery
   objectives, workload, latency and budget. Section 1 of the proposal contains
   starting targets, not proven attainable service guarantees.
5. Assign owners and capacity for labels, adjudication, ongoing content review,
   incident response, and security sign-off.

Phase 0 and local engineering can begin with non-sensitive data; do not
connect real customer data or ship production until these decisions are made.
Keep an explicit decision log in the implementation PR or deployment records.

## 3. Delivery sequence

Dependencies: **0 -> 1 -> 2** for measuring and improving quality. Phase 3
can start after phase 0, but its final authorization contract must be settled
before phase 4 migration. Phase 4 needs the reliability and access controls
from phase 3. Phase 5 requires all prior exit criteria. Existing estimates
(0: 1 week; 1: 2-3; 2: 3-4; 3: 3-4; 4: 3-4; 5: 2-3) assume dedicated staff,
available domain reviewers and infrastructure; revisit after phase 0.

### Phase 0: establish a reproducible baseline

**Owner:** engineering, with product and domain reviewers.

1. Inventory the deployed path and configuration, datasets, index contents,
   models, prompt versions, cache setting and dependency versions. Record a
   source commit and document/index snapshot IDs. Keep sensitive content out
   of the report.
2. In an isolated environment, with permission for model calls and cost, run
   the existing routing, NIST and dishwasher batch datasets and the chat
   regression against the same registry/index as the API. Run fresh model calls
   with `ROUTING_LAB_CACHE_ENABLED=0`; record failures, sample counts, cost
   and wall-clock latency. Existing scripts and their documented options are
   in the [README](../README.md); do not imply their substring scores measure
   semantic correctness.
3. Review a small, representative sample manually, including unanswerable
   questions and all answer paths. Separate routing, retrieval, generation,
   synthesis, condensation and ingestion failures. Record service assumptions
   and propose cost and latency budgets.
4. Agree on the evaluation and deployment decisions in section 2. Do not
   start MLflow automatically: local tracing stays on demand.

**Exit:** versioned baseline report with commands, configuration, denominators,
known limitations and owners; agreed initial budgets and decision owners.

### Phase 1: evaluation foundation

**Owner:** evaluation engineering and domain reviewers. Depends on phase 0.

1. Define a versioned case schema alongside
   [existing datasets](../datasets): ID, source snapshot and expected evidence
   spans, question and prior turns, scope/permissions, answerability, expected
   facts or acceptable outcomes, route/tool expectations where applicable,
   slice labels and reviewer status. Include KB, uploaded, direct attachment,
   history, multi-topic, multi-hop, tool, ambiguity, contradictory/stale,
   no-evidence and injection cases. Keep raw confidential examples outside
   the repository.
2. Assemble 300-500 reviewed cases as the initial corpus. Split by
   document/source and related conversation family, not just question, into
   tuning and access-controlled held-out sets; preserve representative
   answerable and unanswerable slices. Identify who can access the holdout,
   log uses and rotate it when contaminated. Add new production-derived cases
   only with permission and appropriate redaction.
3. Extend the existing [batch runner](../scripts/run_batch_tests.py) and
   [chat runner](../scripts/run_chat_batch_tests.py), rather than counting a
   routing-only pass as answer quality. Add a reproducible evaluation entry
   point that records case, config/model/prompt/index versions, answer,
   evidence, outcomes, errors, token/cost and timing. Use the actual API
   path for chat/attachments, with separate browser/stream tests.
4. Define a human rubric for correctness, claim support, citation support,
   abstention and severity. Blind two reviewers to system identity on a
   stratified sample; record disagreement, adjudication and inter-rater
   agreement. Calibrate any LLM judge on separate human labels and measure
   disagreement and false approvals; it supplements, not replaces, human
   judgment. Failed judge calls are errors, never automatic passes.
5. Produce machine-readable and human-readable scorecards with numerator,
   denominator, exclusions and uncertainty per metric/slice. Report missing
   labels or insufficient samples as **inconclusive**, not zero or pass.
   Propose minimum slice sizes and review frequency for owner approval.

**Exit:** reviewed corpus and protected holdout; documented rubric and judge
calibration; one repeatable uncached run produces the scorecard and a nonzero
exit on a failed or incomplete gate. No production readiness claim yet.

### Phase 2: accuracy and evidence

**Owner:** application and evaluation engineering. Depends on phase 1; coordinate
the evidence contract with phase 3 authorization.

1. **Evidence contract.** Extend [routing state](../app/state.py),
   [chat state](../app/chat/state.py) and
   [routing summary](../app/chat/routing_summary.py) with versioned,
   structured evidence IDs and answer status. Record source type, document
   ID/version, chunk or span, page when available, and successful tool
   input/output provenance. Give citations stable, unambiguous IDs across
   topics and hops. Define equivalents for current-turn attachments and
   conversation history; do not pretend image/OCR text has page-level
   support if it does not. Keep old stored turns readable and mark them
   as unchecked, never retroactively verified.
2. **Generation and checking.** Update
   [topic agents](../app/agents/_shared.py) to generate claims with evidence
   references. Validate IDs, source visibility and structured output, then
   assess each material claim against its cited evidence and tool output.
   Check the **final** answer after synthesis/multi-hop and the attachment
   and history branches before output and persistence. Check hop-one values
   before they influence hop two. If the final answer is changed by a
   guardrail, ensure its citations/status match the delivered text.
3. Use a bounded retry for unsupported, contradictory or incomplete answers.
   If still uncertain or the verifier is unavailable, return an explicitly
   qualified supported partial answer only if that part passed verification;
   otherwise decline. Never treat a checker verdict as a guarantee. Keep
   existing output/error handling explicit and apply the same policy to
   synchronous and streaming endpoints; do not stream unverified answer text.
4. **Citations and UI.** Extend both API responses and persisted turns with
   cited evidence, status and schema version. Update
   [RoutingDetails](../frontend/src/components/RoutingDetails.tsx) and
   [PassagePreview](../frontend/src/components/PassagePreview.tsx) to show
   claim-linked, automatically checked citations separately from other
   retrieved passages. Keep older responses usable. Source access must be
   reauthorized when opened or restored.
5. **Retrieval and abstention.** Benchmark similarity, hybrid and reranking
   on the tuning set using [comparison script](../scripts/compare_retrieval_modes.py);
   extend it if required to cover uploads, routing, parameters and full
   end-to-end outcomes. Measure recall, correctness, abstention, latency and
   cost before changing defaults. Calibrate any relevance gate by mode and
   version on labeled data; test false declines and conflicting/stale sources.
   Add metadata filtering and out-of-scope/clarification behavior without
   bypassing authorization. Test exact terms, missing evidence and version
   replacements.
6. Version model aliases and prompts, record actual provider model/version
   where available and snapshot the index. Run model and prompt changes through
   the same gate; do not assume provider aliases are immutable.

**Verification:** focused unit tests for invalid citation IDs, unsupported
claims, verifier failure, bounded retries, successful and failed tools;
integration tests for curated and uploaded sources, synthesis, multi-hop,
attachments, history, old checkpoints, stream and sync. Compare to baseline
on the untouched holdout and check both unsupported answers and false declines.

**Exit:** approved thresholds met with sufficient labeled data; final answer
paths and citation persistence tested; latency/cost trade-offs documented.
Roll out behind an explicit flag in staging; production enables the policy
only after the release gate, with no silent fail-open.

### Phase 3: production security and reliability baseline

**Owner:** backend, security and platform engineering. May proceed alongside
phase 2 after phase 0; access model requires section 2 approval.

1. Add explicit development/production profiles. Production validates required
   configuration and secrets at startup; no in-memory checkpointer, local
   registry or direct-provider budget bypass unless explicitly approved in the
   deployment design. Specify required services, and make missing credentials,
   initialization or security controls visible failures. Keep dev defaults.
2. Harden identity and authorization in [auth.py](../app/api/auth.py) and
   [API](../app/api/main.py): validate the IdP contract; add server-side
   user/KB-editor/admin authorization, deny by default, and audit changes.
   If isolation is required, apply tenant/document permissions before retrieval
   in **all** vector and keyword paths, retries, tools, attachments, source
   previews, history and caches; recheck on reads and permission changes.
   Verify cross-user, cross-tenant and privilege-revocation cases. No rollout
   of sensitive data until the chosen access model is tested.
3. Add bounded timeouts, retry budgets with backoff/jitter and circuit
   breaking where justified for provider, embeddings, database and gateway.
   Respect request deadlines and cancellation, avoid retries for unsafe
   mutations, and surface service failures rather than fabricating answers.
   Separate liveness from dependency readiness; test startup, shutdown,
   dependency loss and recovery.
4. Treat user input, retrieved documents, attachments, tool output and
   conversation history as untrusted. Enable production guardrails with
   explicit failure handling; add tested prompt-injection, secret/PII and
   policy controls appropriate to the approved use case. Scanner results
   are defense in depth, not a security guarantee. Apply upload limits,
   file validation, malware scanning and isolated extraction according to
   approved operational policy.
5. Add API edge throttling, request-size limits, TLS, restricted CORS and
   security headers. Set up production IdP persistence, MFA/SSO and a secret
   manager; do not reuse development accounts or keys.
6. Add a non-root backend container and reproducible dependency locking.
   Update [Azure pipeline](../../azure-pipelines.yml) or add a lab 7 pipeline
   without breaking lab 3. Gate lab 7 changes with offline unit/API tests,
   frontend `npm run lint`, `npm test`, `npm run build`, relevant Playwright
   tests, dependency scans and image build. Run paid/credentialed live tests
   only in controlled CI environments. Preserve explicit skip/failure reporting
   for unavailable integrations.

**Exit:** staging deployment with required controls enabled; permission,
dependency-failure and malicious-input tests pass; security owner reviews
exceptions. A passed fixed red-team set is not proof of security.

### Phase 4: shared storage, scalability and operations

**Owner:** platform, data and backend engineering. Depends on phase 3's access
model and production controls.

1. Select the shared vector/search and object stores after verifying filtering,
   capacity, backup, regional and operational requirements. Replace the local
   Chroma and file-storage assumptions via existing ingestion/retrieval
   interfaces. Maintain version and authorization constraints in both dense
   and keyword retrieval; do not expose unauthorized candidates to the model.
2. Replace the process-local publication lock with durable coordination.
   Make ingestion idempotent and recoverable through a durable job mechanism.
   Stage each version, validate it, atomically switch an authoritative active
   version and retire old chunks later. Handle duplicate jobs, concurrent
   replacements, worker crashes and partial cleanup. Ensure registry, objects,
   vectors and keyword index resolve the same active version.
3. Rebuild a versioned candidate index from originals in staging; compare
   counts, metadata, access filters and retrieval/answer results with the
   old index. Define a consistent cutover window and rollback including writes
   during migration. Do not change production writes until rollback is
   rehearsed; retain the old index until retention and rollback policies allow
   removal.
4. Add privacy-reviewed structured logs, trace/request correlation, metrics
   and alerts for errors, latency, cost, verification/abstention, ingestion
   and dependency health. Restrict access and retention; avoid raw sensitive
   questions, documents, keys and model payloads by default. Local MLflow
   remains opt-in/on demand; select an approved deployed telemetry service
   separately.
5. Load test at approved concurrency with at least two replicas; include
   provider failures, upload/replacement races and restart scenarios. Measure
   p95 end-to-end latency, availability/error rate, resource usage and cost
   against signed-off SLOs. Document alerts, on-call runbooks and escalation.

**Exit:** multi-replica staging passes concurrency, isolation and failure
tests; cutover and rollback rehearsed; load/SLO and alert drills pass.

### Phase 5: governance, feedback and launch

**Owner:** product, security, operations and domain owners. Depends on phases
1-4 and decisions in section 2.

1. Document data flows, provider terms, residency, access, encryption,
   retention and deletion across checkpoints, attachments, originals,
   indexes, caches, logs, traces and backups. Test deletion and restore; define
   backup retention, recovery point/time objectives and responsibility.
2. Add answer feedback with explicit user consent, trace correlation and
   restricted triage access. Review negative/declined answers and sample
   successful answers; turn confirmed, sanitized failures into tuning or new
   independently held-out cases, not both.
3. Write model/system cards, known limitations, source-owner review cadence,
   incident response, change approvals and an evidence-to-control mapping for
   the selected compliance framework. A mapping does not constitute
   certification.
4. Conduct a controlled pilot with approved users/data. Compare independently
   reviewed pilot outcomes and slice distributions against the offline
   scorecard; triage discrepancies. Obtain product, domain, security and
   operations sign-off before production promotion.

**Exit:** restore and incident drills pass, pilot and release criteria pass,
risks are accepted by named owners, and support/rollback is staffed.

## 4. Metrics and release gate

Agree the exact rubric and statistically adequate sample sizes with owners
before enforcing the proposal's initial targets. Report 95% confidence
intervals; avoid treating correlated claims in the same answer or related
questions as independent samples. Use answer/conversation-level resampling
where appropriate, and disclose small or unrepresented slices.

| Metric | Measurement population and proposed decision rule |
| --- | --- |
| Faithfulness >= 98% | Human-adjudicated supported material claims / all material claims in delivered substantive answers, including uncited claims. Also report answer-level share with any unsupported claim. |
| Answer correctness >= 95% | Correct and complete answers / answerable evaluated cases, using the reviewed rubric; incorrect extra claims count against correctness. |
| Citation validity >= 95% | Supported, resolvable claim-to-citation links / all claim-to-citation links; separately report citation coverage over material claims so uncited claims cannot improve the score. |
| Correct abstention >= 95% | Appropriate decline or clarification / cases labeled unanswerable, out-of-scope or requiring clarification. Score these slices separately too. |
| False abstention <= 5% | Unnecessary decline or clarification / answerable cases, including evidence sufficient for a supported partial answer when the rubric permits it. |
| Routing >= 97% | Cases with all applicable expected routing decisions correct / cases with reviewed routing labels. Report topic, subtopic and chapter separately; mark routes with no applicable label N/A. |
| Known attack suite | All reviewed known prompt-injection/leakage regression cases meet their expected safe outcomes; ordinary benign control cases must also remain usable. |

Use the protected heldout set, uncached calls and a pinned candidate snapshot.
Judge-only scores are provisional until calibrated against human review;
prespecify how much human review is required for release. Empty or missing
denominators, errors and inadequate samples block the relevant gate, not pass
it. Report both point estimates and intervals; product and domain owners must
approve in advance whether the decision rule uses point estimates or confidence
bounds and the allowed slice regression margin. No retroactive threshold
changes to pass a candidate.

Every release candidate also requires passing offline unit/API/UI tests,
integration and stream tests, access-control and red-team regressions, scans
with reviewed exceptions, and the agreed performance/SLO tests. Re-run the
full accuracy gate for changes to model, prompt, routing, chunking, embedding,
retrieval, verifier or knowledge snapshot. The fast PR tier is a smoke test,
not proof of quality. Keep scorecard, config, artifacts and approval records
with the release; unknown results block promotion. Roll back application and
index versions together using the rehearsed procedure if post-release
monitoring or security triggers are breached.

## 5. First implementation increments

1. Agree section 2 decisions and establish phase 0 baseline, without changing
   live configuration.
2. Add the evaluation schema, reviewed tuning data, holdout governance and
   scorecard with deterministic offline tests. Obtain real domain labels
   rather than inventing answers or treating existing fact substrings as truth.
3. Define and test the versioned evidence/answer contract before implementing
   verifier or frontend changes. Then implement final-answer checking and UI
   support together, using an explicit rollout flag.
4. Build staging security and reliability controls and the lab 7 CI path in
   parallel; do not claim readiness until all later phases and the release gate
   pass.
