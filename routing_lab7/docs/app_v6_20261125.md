# Routing Lab 6: application feature inventory

This document describes the features implemented in `routing_lab7` as a
baseline for future feature requests. It describes the code, not a guarantee
that every optional service is running or that model-generated answers are
correct. Configuration, indexed documents, and enabled services can change
the behavior of a particular installation.

## 1. Application at a glance

The application combines:

1. A React chat interface for conversations, attachments, and knowledge-base
   management.
2. A FastAPI service with authenticated chat, document, and conversation APIs.
3. A LangGraph chat workflow and a separate routing/retrieval/answer workflow.
4. A curated knowledge base and a shared, uploadable document index.
5. A Streamlit developer dashboard, evaluation datasets, batch runner, and
   comparison scripts.
6. Optional PostgreSQL persistence, LiteLLM per-user budgeting, MLflow tracing,
   hybrid retrieval, reranking, and chat guardrails.

The user-facing chat and the developer dashboard serve different purposes:
the dashboard runs individual questions through the routing graph, while
chat adds authentication, conversation history, attachments, and follow-up
question handling.

## 2. Chat interface

### Conversations and navigation

- The interface is titled **Knowledge Base Chat** rather than being tied to a
  single topic. It displays the active conversation title and provides a
  responsive sidebar, including a mobile overlay.
- Users can start a conversation, select a previous conversation, and search
  the sidebar by title. The list is ordered by recent activity.
- A new conversation initially uses its first message as a title. After the
  first completed turn, the backend attempts to generate a short descriptive
  title; a user-supplied rename is retained instead of being overwritten.
- Users can rename conversations and delete them through a two-step
  confirmation. A deleted conversation has a short, eight-second **Undo**
  affordance in the interface.
- The normal delete is a soft delete; old soft-deleted conversations are
  purged during backend startup after 30 days. The API also supports immediate
  permanent deletion. Undo in the UI is brief even though the backend restore
  endpoint has a longer window before purge.
- The browser stores the selected thread ID locally. Reloading or selecting a
  conversation restores its saved messages, attachment metadata, and routing
  summaries. Live execution timings are not restored from history.
- Conversation switching and creation are disabled while a message is in
  flight. Loading and network failures are surfaced in the chat with retry.

### Asking and reading questions

- The composer accepts text, attachments, or both. **Enter** sends;
  **Shift+Enter** inserts a newline. The text area grows up to a bounded
  height, then scrolls.
- Empty conversations display clickable example prompts. The interface
  preserves a user's position when they scroll up and provides **Jump to
  latest** when appropriate.
- Assistant answers render sanitized Markdown and have a copy button. The
  last completed answer can be **Regenerate**d: this submits the most recent
  user message again as a *new conversation turn*, not an in-place replacement.
- Live responses show progress as graph nodes finish. The final answer arrives
  as one complete answer event, not token-by-token text streaming.
- **Stop** cancels the browser's wait, not necessarily backend execution.
  The turn may still finish on the server and appear after history is reloaded.
  Failed sends can be retried with their original text and attachments.
- Light and dark themes are available. The first visit follows the operating
  system preference; the chosen theme is saved in browser local storage.
- The frontend requires Keycloak sign-in, offers sign-out, refreshes access
  tokens, and can warn shortly before session expiry with an option to stay
  signed in.

### Message attachments versus knowledge documents

Message attachments belong to a conversation and are not automatically
added to the shared searchable knowledge base. The separate Knowledge Base
Manager performs indexing, described in section 5.

- Attach via file picker, drag and drop, or paste. The UI shows pending
  uploads, image previews, errors, and an option to remove an attachment
  before sending.
- Supported content is PNG, JPEG, WebP, GIF, PDF, and UTF-8 text. The server
  identifies the type from content rather than trusting the supplied filename
  or content type. The limit is **5 MiB per file** and **four attachments per
  message**.
- The frontend attempts to downscale large images to a maximum long edge of
  1,568 pixels before upload. The backend uses a vision-model call to extract
  an image description and visible text once at upload time. PDF and text
  extraction is local.
- Extracted attachment content is limited to 8,000 characters. An image-only
  or unreadable PDF can yield no text; the UI warns when a document attachment
  has no readable text. This path does not provide PDF OCR.
- When the question is about the attachment itself, the chat can answer from
  extracted attachment content. When the attachment supplies context for a
  knowledge question, the condensed question can incorporate those details
  and continue through knowledge-base routing.
- Attachments are stored per thread, and downloads and chat references are
  checked against conversation ownership and thread membership. Stored files
  and history persist only when the appropriate persistent backend is set up.

## 3. Conversation intelligence and routing

### Chat workflow

For each turn, the chat graph:

1. Optionally checks the input with guardrails.
2. Uses an LLM to rewrite the latest message into a self-contained question,
   using previous turns to resolve references such as "it".
3. Routes questions about the conversation to an answer based on conversation
   history, questions about attached files to extracted attachment content,
   or knowledge questions to the routing graph.
4. Optionally checks the outgoing answer and records the turn and a compact
   routing summary in the conversation.

These are model decisions, so follow-up resolution and intent classification
can be wrong. Conversations use a thread-specific LangGraph checkpointer:
in-memory by default, or PostgreSQL when `CHAT_DB_URL` is configured.

### Knowledge routing workflow

The main graph implements the following stages:

- **Complexity and multi-hop classification.** A genuinely dependent two-hop
  question can be decomposed: the first hop is answered, a value is extracted,
  and that value is used to form the second question. Each hop uses the
  routing pipeline. A refused first hop is not used as a second-hop fact.
  Recursive hop subquestions skip multi-hop classification to prevent
  unbounded nesting.
- **Topic selection and clarification.** Questions can select one or
  multiple topics. An ambiguity decision can send the user a clarification
  question instead of proceeding with a guessed route.
- **Subtopic and chapter selection.** A subtopic and a chapter are chosen for
  each selected topic. Chapter selection is visible for inspection and
  evaluation; retrieval is scoped to the topic and subtopic, **not** to only
  the selected chapter.
- **Retrieval and tool selection.** The system retrieves relevant passages
  and can select a calculator, a structured-data query, or a metadata lookup.
- **Specialist agents and synthesis.** Topic-specific agents answer using
  retrieved evidence and successful tool results. Multi-topic requests fan
  out to agents and combine their answers. A declined component is preserved
  rather than silently presented as a fully supported combined answer.
  Approved custom topics use a generic topic agent.
- **Section-reference hint.** For a recognizable exact section identifier
  such as `MANAGE 4.3`, the topic router can receive a hint when that
  identifier occurs in exactly one visible topic. Missing or shared references
  do not disambiguate a topic; this is not general semantic disambiguation.

## 4. Retrieval, answers, and inspection

### Search and answer generation

- Curated Markdown chapters and uploaded chunks share a local persistent
  Chroma collection. Default embeddings use `text-embedding-3-small`; default
  similarity retrieval requests the top five results.
- Optional `hybrid` retrieval combines vector search and BM25 keyword search.
  Optional cross-encoder reranking retrieves a wider candidate set and
  reorders it. These options are disabled by default.
- For a topic/subtopic containing uploads, normal first-pass results are
  supplemented with up to ten hybrid candidates, deduplicated against the
  original results.
- The specialist agent is instructed to answer from retrieved passages and
  successful tool results, or say the knowledge base has insufficient
  information. This is a prompt-based behavior, not a guarantee of
  factuality.
- Answers supported by uploaded passages receive an additional LLM-based
  relevance and support check. A declined answer, failed tool, or failed
  support check can trigger **one** recovery attempt: the system broadens
  search across the topic using hybrid retrieval and may correct a failed
  tool input. A still-unverified answer is withheld. The check and retry
  add model calls, latency, and cost and can themselves be wrong.
- Source lines are constructed from retrieved metadata. For uploads they can
  include filename, document ID, version, and available PDF page numbers.
  **These are retrieved-passage references, not verified citations**: a
  listed passage may not support every claim in the answer.

### Routing details in chat

Completed turns can expose a collapsible **Routing details** panel containing:

- Topic, subtopic, and selected chapter breadcrumbs.
- Recovery status and reason, when a retry occurred.
- Multi-hop questions, answers, and extracted values where applicable.
- Selected tool name, input, output, or error.
- Retrieved passage cards with source/chapter, page, version, score, and
  excerpt where available. Selecting a card opens a fuller passage preview.
- A node execution timeline with durations for a live-streamed turn. This
  timeline is not persisted in restored history.

Retrieval scores depend on the retrieval mode: Chroma distance, hybrid
rank-based values, and reranker scores are not interchangeable measures of
answer confidence.

### Available tools

| Tool | Implemented use and boundary |
| --- | --- |
| Calculator | Evaluates numeric expressions with `+`, `-`, `*`, `/`, and parentheses using a restricted syntax tree. |
| SQL query | Queries a topic/subtopic's existing `specifications.csv` in a temporary in-memory SQLite table; intended for read-only lookups such as exact model prices. It is not a general database or arbitrary uploaded-file query tool. |
| Metadata lookup | Returns a curated subtopic chapter count or a curated chapter's version using a fixed input syntax. |
| Document search | A `NotImplementedError` stub and not offered to the tool router; normal retrieval is a separate, working stage. |

## 5. Knowledge Base Manager and ingestion

### Upload and review

- Open the Knowledge Base Manager from chat to browse or drag and drop one or
  more documents. Accepted server-side content is PDF or UTF-8 text, including
  text formats such as Markdown, CSV, and JSON. Files are limited to 5 MiB.
  Content is sniffed rather than trusted solely by extension.
- Upload returns a processing record; a separate background LangGraph
  workflow validates, extracts, classifies, chunks, indexes, tests
  retrieval, and publishes the document. The UI polls processing records
  every two seconds.
- The manager lists **Processing**, **Indexed**, **Needs review**, and
  **Failed** states. Expanding a record shows classification, confidence,
  chunk count, version, errors, and timed pipeline events. A pending
  replacement and its version are also displayed.
- Classification uses the filename and the first 6,000 extracted characters.
  It proposes a single topic and subtopic plus chapter labels. Unknown
  categories or confidence below `0.6` are parked for review; the model's
  confidence is not a calibrated probability.
- Reviewers can approve a suggestion, request a fresh suggestion for a
  document awaiting review, choose an existing category, or create a missing
  topic/subtopic and reclassify. New identifiers begin with a lowercase
  letter, contain only lowercase letters, digits, or underscores, and are at
  most 64 characters. Manual classification sets confidence to `1.0` as an
  override, not as measured model confidence.
- Approved taxonomy additions are shared with routing and persist in
  PostgreSQL when configured, otherwise in `data/taxonomy.db`.
- Knowledge documents are shared among authenticated users; per-document
  permissions are not implemented. The current manager/API does not provide
  a document-delete action.

### Extraction, chunking, and publication

- PDF extraction retains individual page numbers. Text is split by paragraph,
  with approximately 1,200-character chunks, sentence-aware splitting where
  possible, and 200-character overlap for oversized splits. Indexed chunks
  carry topic, subtopic, document ID, filename, version, and page where known.
- Image-only/scanned PDF pages are not OCR'd; the ingestion pipeline can
  fail explicitly instead of pretending they are searchable.
- Before publication, retrieval is probed using samples from the first,
  middle, and last chunks. These probes test findability, **not** whether
  generated answers are correct.
- Duplicate bytes return the existing document rather than indexing again.
  Changed content uploaded with the same filename starts a replacement
  version; ambiguous duplicate filenames are rejected.
- During replacement or re-indexing, the previously published version remains
  searchable while the new version is processed or reviewed. Once the new
  version is ready, it is published and old chunks are cleaned up. A failed
  replacement can be retried; interrupted replacements are marked failed on
  startup.
- **Re-index stored file** reprocesses an indexed document's original even if
  unchanged. The backend verifies that the stored file matches its recorded
  hash before starting. Manual reclassification of an existing document
  without a pending replacement follows a different path that removes its
  existing indexed chunks before reprocessing.
- Publication coordination uses a process-local lock; multiple backend
  workers sharing the same index are not an atomic publication setup.
- The curated index builder supports incremental updates. A full rebuild
  (`--rebuild`, or a rebuild triggered by missing/incompatible manifest
  state) can replace the entire collection with curated content and remove
  uploaded chunks. Treat it as a data-affecting operation, not a routine
  read-only test.

## 6. API, identity, and persistence

### API surface

| Endpoint | Purpose |
| --- | --- |
| `GET /health` | Basic service health response. |
| `POST /chat` | Synchronous turn; returns the condensed question, answer, routing summary, and guardrail status. |
| `POST /chat/stream` | Server-sent progress events followed by a complete answer or an error event. |
| `GET /threads` | List the signed-in user's conversations. |
| `GET /threads/{thread_id}/history` | Restore a conversation's turns. |
| `PATCH /threads/{thread_id}` | Rename a conversation. |
| `DELETE /threads/{thread_id}` | Soft delete; `permanent=true` requests immediate permanent deletion. |
| `POST /threads/{thread_id}/restore` | Restore a soft-deleted conversation before purge. |
| `POST /threads/{thread_id}/attachments` | Upload and extract one thread attachment. |
| `GET /threads/{thread_id}/attachments/{attachment_id}` | Fetch an owned thread attachment. |
| `POST /knowledge/documents` | Upload, deduplicate, or begin replacement of a shared knowledge document. |
| `GET /knowledge/documents` and `GET /knowledge/documents/{document_id}` | List documents or inspect one document and its ingestion events. |
| `POST /knowledge/documents/{document_id}/reindex` | Reprocess an eligible indexed document's stored original. |
| `GET /knowledge/taxonomy` | Read built-in and approved topic/subtopic pairs. |
| `POST /knowledge/documents/{document_id}/suggestion` | Request a fresh classification for a document awaiting review. |
| `POST /knowledge/documents/{document_id}/classification` | Apply an approved/manual classification and resume indexing. |
| `POST /client-error` | Record a frontend error report. |

Except for health, application routes require a verified bearer token.
Keycloak access tokens are verified for signature, issuer, and expected
authorized client; the token subject identifies the conversation owner.
Conversation operations check ownership. Knowledge documents, by contrast,
are shared across authenticated users.

### Persistence and services

- With `CHAT_DB_URL`, PostgreSQL stores conversation checkpoints, ownership,
  attachments, document registry, and approved taxonomy; optional LiteLLM
  user-key mappings can also persist there. Without it, conversation state,
  attachment records, and the document registry are in memory and disappear
  on backend restart; taxonomy additions use local SQLite instead.
- Uploaded originals are stored locally under the project's `data` directory.
  The Chroma index persists separately under `.chroma`. Durable original
  files and vector data alone do not replace a durable document registry.
- Standalone scripts that search uploaded replacement versions must be
  configured to use the same persistent registry/database as the backend.
  Otherwise their view of active document versions can differ.
- Docker Compose supplies local-development Keycloak, PostgreSQL, and
  LiteLLM services. The included Keycloak dev-mode and gateway settings are
  not a production-hardened deployment.
- If `LITELLM_BASE_URL` is configured, requests can use per-user virtual keys
  and budgets; without it, calls use the directly configured provider key
  and do not have this per-user budget mechanism.
- Optional guardrails, off by default, scan incoming messages for prompt
  injection and outgoing answers for a limited set of credential patterns.
  A blocked input or redacted output receives a visible status. These checks
  are not comprehensive security or factuality guarantees.

## 7. Developer dashboard, observability, and testing

### Dashboard and tracing

The [Streamlit dashboard](../dashboard/streamlit_app.py) provides:

- A graph visualization, with Mermaid source fallback if image rendering is
  unavailable.
- Cache and MLflow tracing status.
- A free-form question runner showing topics, subtopics, chapters, final
  answer, retrieved passages, raw router decisions, and execution trace.
- Evaluation of **Levels 1, 2, and 3** in the dashboard: topic, subtopic,
  and chapter routing respectively, with expected/actual rows and metrics.
  Other evaluation capabilities are available through scripts and datasets;
  the dashboard selector itself is limited to those three levels.

MLflow tracing is optional and used only when its tracking server is
reachable; the tracing helper does not start the server. It is intended to be
started on demand, not automatically at login or boot. A local persistent
SQLite cache for LLM and embedding calls is enabled by default and can be
disabled with `ROUTING_LAB_CACHE_ENABLED=0` when fresh calls are needed.

### Batch questions and regression reports

- [Batch runner](../scripts/run_batch_tests.py) invokes the routing graph
  independently for each dataset question. It can select specific IDs,
  accept a different JSON dataset and output directory, and optionally run
  an additional `--llm-judge`.
- The runner writes a summary CSV, detailed JSON, readable Markdown report,
  and manual-review CSV; it also attempts to write a Mermaid graph. Manual
  review notes are retained by test ID across reruns in the same output
  directory.
- Per-case routing dimensions can include topics, subtopics, chapters,
  retrieved sources, tools, clarification behavior, multi-hop behavior,
  and recovery. Routing correctness and answer correctness are reported
  separately.
- Automated expected-fact scoring mainly checks case-insensitive substrings,
  with limited normalization for year durations. The groundedness metric is
  lexical overlap, not semantic proof. The optional LLM judge is approximate,
  incurs additional calls, and does not change deterministic pass/fail.
  Inspect the actual answer, passages, and manual-review fields rather than
  treating a pass as proof.
- The standalone batch graph is stateless between questions; it does not
  exercise chat history, authentication, browser behavior, or follow-up
  condensation.
- The repository includes a general
  [batch dataset](../datasets/batch_test_questions.json), a
  [NIST AI RMF dataset](../datasets/nist_questions.json), and a
  [dishwasher manual dataset](../datasets/dishwasher_manual_file2_questions.json).
  The NIST dataset has a companion
  [human-readable question and answer guide](./q_and_a/NIST.AI.100-1.md).

Example from the `routing_lab7` directory, after configuring the same
database/index as the application:

```powershell
python scripts\run_batch_tests.py --dataset datasets\nist_questions.json --output-dir outputs\nist_regression
```

Add `--ids` followed by test IDs to run a subset, or `--llm-judge` for the
additional approximate assessment. These commands can make model calls and
incur cost; existing cached answers may be reused unless caching is disabled.

## 8. Configuration reference

| Setting | Default or effect |
| --- | --- |
| `ROUTING_LAB_MODEL` | Router and agent model; defaults to `gpt-4o-mini`. |
| `ROUTING_LAB_RETRIEVAL_MODE` | `similarity` by default; `hybrid` is optional. |
| `ROUTING_LAB_RERANK_ENABLED` | `0` by default; `1` enables optional cross-encoder reranking and its model dependencies. |
| `ROUTING_LAB_GUARDRAILS_ENABLED` | `0` by default; `1` enables the optional input/output checks. |
| `ROUTING_LAB_CACHE_ENABLED` | Enabled by default; `0` disables the persistent response/embedding cache. |
| `CHAT_DB_URL` | Enables PostgreSQL-backed chat and registry persistence; absent means in-memory state for those components. |
| `LITELLM_BASE_URL` | Enables the optional LiteLLM gateway and user-key provisioner when configured with its required credentials. |
| `MLFLOW_TRACKING_URI` | Overrides the tracking endpoint used when the optional MLflow server is reachable. |
| `KEYCLOAK_ISSUER`, `KEYCLOAK_CLIENT_ID` | Configure backend token verification. |
| `CHAT_API_CORS_ORIGINS` | Comma-separated allowed frontend origins. |
| `VITE_KEYCLOAK_URL`, `VITE_KEYCLOAK_REALM`, `VITE_KEYCLOAK_CLIENT_ID` | Configure the frontend's Keycloak connection. |

The embedding model, default retrieval count, reranker model, topic definitions,
and guardrail threshold are defined in [configuration](../app/config.py).
Sensitive credentials should be supplied through the environment and not
added to this document.
